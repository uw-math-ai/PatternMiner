# Design a model for mathematical pattern discovery

Ask what learning could reveal about the mathematical question. Choose a task that exposes a useful relation or operation: predicting an invariant, learning a map, selecting a witness, proposing constructions, or modeling an unexplained residual. Explain how the predictions, errors, or learned computation could suggest a conjecture. Consult the [model-design guide](../guides/model-design.md) and relevant primary papers.

Describe the mathematical objects, their representation, permissible inputs, target, and known symmetries. Specify whether the target is invariant or equivariant under each transformation. Preserve necessary positional, incidence, or algebraic information. Do not use answer-equivalent oracle outputs as features while claiming a harder prediction task.

When information loss is a plausible explanation, look for distinct objects with identical proposed features but incompatible targets. For a task with several valid outputs, disjoint valid-output sets give a stronger obstruction than different preferred labels. Such examples can identify missing mathematical information before further training and can furnish matched inputs for mechanistic interventions.

Choose an elementary baseline and a small, sufficiently expressive model. Justify the architecture by the data and the proposed operation; do not default to a transformer for every representation. Specify enough training details for a bounded pilot: data construction, split, objective, size, optimizer, seeds, checkpoint selection, metrics, and resource estimate. Confirm that the pilot lies within the project's approved allocation before running it.

Check for label-dependent preprocessing and overlap between equivalent objects or generating families. Distinguish generalization to new examples, sizes, families, and sampling procedures. With multiple valid outputs, recognize mathematical validity rather than only matching an arbitrary selected label. Preserve exact targets if training uses normalization or approximation.

Use the pilot to diagnose learning, representation, and sampling issues. Compare errors by mathematical family. Test implemented symmetries. If the model cannot fit a small training subset, first investigate the task, data, masking, and optimization. If it fits but fails on new families, investigate shortcuts and missing structure. Scale or retrain only when the next change addresses a concrete uncertainty.

Before trying to recover a dependable mathematical algorithm from the model, require near-perfect mathematical correctness on a stated domain. Set the operational threshold and assessment populations before tuning. Check difficult examples, meaningful changes of presentation, and the intended generalization to new sizes or families separately; a high aggregate score can hide failure on the distinction being investigated. Report counts, uncertainty at the mathematical grouping level, and prior exposure of assessment data. A finite test does not establish correctness in general.

When an input includes a supplied certificate or a nonunique auxiliary choice, test the valid alternatives explicitly. Report whether an object is answered correctly for every tested choice, in addition to average input accuracy. If a mathematical symmetry is used for augmentation, verify transformed labels and representations and keep equivalent examples out of fresh assessment groups. Distinguish fitting a mined error set from improving accuracy on new mathematical objects.

If this requirement is not met, make improving the research instrument the next task. Compare training fit with separated-family performance, and test concrete changes to representation, supervision, sampling, or optimization within the remaining allocation. Defining a mathematically natural restricted domain can be useful, but selecting easy cases after observing failures does not establish reliability on the original domain.

Design for inspection: retain checkpoints and expose relevant weights, activations, attention outputs, and model outputs. Explicitly consider the [mechanistic-interpretability prompt](mechanistic-interpretability.md), distinguishing diagnosis of errors from extraction of an algorithm. Diagnostic interventions can help improve an imperfect model; an extensive circuit reconstruction should wait for reliable behavior on the target domain. Model simplification, multiple seeds, or training checkpoints can help distinguish explanations; they require a reason and a resource allocation.

If an internal pattern suggests a mathematical relation, use the [conjecture prompt](conjecture.md) even when the mechanism is only partly understood. Record whether the conjecture arose from predictions, selected examples, representation inspection, or interventions. A useful model need not produce a theorem, and a useful conjecture need not await further training.
